# Llama 4 Maverick FP8 with an FP8 KV cache on p6-b200.48xlarge, tensor parallel 8, FlashInfer attention

Serves the published FP8 checkpoint of [`meta-llama/Llama-4-Maverick-17B-128E-Instruct-FP8`](https://huggingface.co/meta-llama/Llama-4-Maverick-17B-128E-Instruct-FP8) as one copy split across all eight GPUs of a p6-b200.48xlarge, using [`fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer.yaml`](../../../vllm-recipes/llama4-maverick/fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer.yaml).

## Capacity sizing

Llama 4 Maverick is a mixture-of-experts model, and every expert stays resident, so the ~388 GiB FP8 checkpoint needs the whole node. Its KV cache is light. 8 KV heads at head size 128 across 48 layers cost 96 KiB per token at FP8, so a full 32,768-token sequence holds 3 GiB. At a 0.90 memory fraction, eight 180 GB B200 GPUs leave roughly 820 GiB after the checkpoint, before activations and CUDA graphs. That is room for about 270 full-length sequences, close to the 256-sequence cap. Read `KV capacity from` and `KV full-ctx seqs` in the result file's provenance block for the allocation in force.

`coding_repo_context` sends about 14.4k wire input tokens and asks for up to 1,024 output tokens, so a request occupies under half a full-length sequence. The 256-sequence cap, not KV memory, bounds the batch for this workload.

| Property | Value | Source |
|---|---|---|
| **Parameters** | ~400B total, ~17B active per token; 128 routed experts, 1 active per token, on every second layer | `config.json` |
| **Layers** | 48 | `config.json`, `num_hidden_layers` |
| **KV heads, head dimension** | 8, 128 | `config.json` |
| **KV cache per token, FP8** | 96 KiB | `2 x 8 x 128 x 1 byte x 48 layers` |
| **Checkpoint size, FP8** | ~388 GiB, 84 safetensors shards | `fetch-weights` init container checks |
| **Instance** | p6-b200.48xlarge, 8x B200 at 180 GB, sm_100, NVLink | `nvidia.com/gpu: "8"` |
| **Tensor parallel size** | 8 | `--tensor-parallel-size 8` |
| **Weight precision** | FP8, compressed-tensors export, dynamic per-token activation scales | checkpoint `quantization_config`; no `--quantization` flag |
| **KV cache precision** | FP8 | `KV_CACHE_DTYPE` |
| **Attention backend** | `FLASHINFER` | `ATTENTION_BACKEND` |
| **Context length** | 32,768 | `MAX_MODEL_LEN` |
| **Max sequences** | 256 | `MAX_NUM_SEQS` |
| **Max batched tokens** | 32,768 | `MAX_NUM_BATCHED_TOKENS` |
| **Memory fraction** | 0.90 | `GPU_MEM_UTIL` |
| **Stream interval** | 10 tokens | `STREAM_INTERVAL` |

## Before you begin

Create the following in the namespace you deploy into. Secrets and ConfigMaps are namespaced.

- [Create an EKS cluster with Karpenter with `./scripts/create-cluster.sh`](../../../scripts/create-cluster.sh)
- [Purchase a p6-b200.48xlarge Capacity Block for ML](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-blocks.html) 
- [Accept the Llama 4 license on Hugging Face](https://huggingface.co/meta-llama/Llama-4-Maverick-17B-128E-Instruct-FP8)

## Quickstart

1. Set environment variables.
   ```bash
   export AWS_REGION=<your-cluster-region>
   export EKS_CLUSTER_NAME=<your-cluster-name>
   export HUGGING_FACE_HUB_TOKEN=<your-hf-token>
   export NAMESPACE=vb-llama4-maverick-fp8kv-32k-flashinfer-p6-b200-48xlarge
   export INSTANCE_TYPE=p6-b200.48xlarge
   export RESERVATION_ID=<your-capacity-block-id>
   ```

2. Install the `eks-bench` CLI into a Python virtual environment.
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -e '.[tokenizer]'
   ```

3. Configure the EKS context and namespace, install the NVIDIA device plugin, create the `hf-token` secret, and grant ECR push permissions.
   ```bash
   ./scripts/install-prerequisites.sh
   ```

4. Provision a Capacity Block GPU node pool with NVMe RAID0 for the instance type.
   ```bash
   ./scripts/provision-capacity-block.sh "$INSTANCE_TYPE" "$RESERVATION_ID"
   ```

5. Install the Pod Identity Agent and grant the `llama4-maverick-bench` ServiceAccount S3 access.
   ```bash
   ./scripts/setup-pod-identity.sh llama4-maverick-bench
   ```

6. Copy the published checkpoint from Hugging Face to your S3 bucket.
   ```bash
   ./model-jobs/llama4-maverick/fp8-model-download.sh
   ```

## Throughput test

1. Deploy the inference server and confirm it serves the model.
   ```bash
   ./vllm-recipes/llama4-maverick/fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer-deploy.sh
   ```

2. Confirm `/models` is on the NVMe RAID0 array, not the EBS root volume.
   ```bash
   kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" exec deployment/llama4-maverick-vllm-b200-fp8kv-32k-flashinfer \
       --container vllm -- df -h /models
   ```

3. Generate the accuracy gate (.JSON) that the benchmark checks against.
   ```bash
   eks-bench capture-reference \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service llama4-maverick-vllm-b200-fp8kv-32k-flashinfer \
       --mode fingerprint \
       --model-tag llama4-maverick --config fp8kv-32k-flashinfer \
       --model-id llama4-maverick \
       --out-dir docs/results
   ```

4. Dry-run the exact in-cluster benchmark.
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service llama4-maverick-vllm-b200-fp8kv-32k-flashinfer \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag llama4-maverick \
       --config fp8kv-32k-flashinfer --quant fp8 \
       --model-id llama4-maverick \
       --tokenizer unsloth/Llama-4-Maverick-17B-128E-Instruct-FP8 \
       --out-dir docs/results \
       --reps 3 \
       --dry-run
   ```

5. Run the benchmark in-cluster. If needed, repeat per protocol, changing `--protocol` and `--profile`. For CLI configurations, see [`docs/guides/REFERENCE.md`](../../guides/REFERENCE.md#measure-flags).
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service llama4-maverick-vllm-b200-fp8kv-32k-flashinfer \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag llama4-maverick \
       --config fp8kv-32k-flashinfer --quant fp8 \
       --model-id llama4-maverick \
       --tokenizer unsloth/Llama-4-Maverick-17B-128E-Instruct-FP8 \
       --out-dir docs/results \
       --reps 3
   ```

## Tear down

```bash
kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" delete \
    -f vllm-recipes/llama4-maverick/fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer.yaml --ignore-not-found
kubectl --context "$EKS_CLUSTER_NAME" delete \
    nodepool/bench-cb-p6-b200-48xlarge ec2nodeclass/bench-cb-p6-b200-48xlarge --ignore-not-found
```

Deleting the server leaves the node empty, and Karpenter scales it to zero. The checkpoint in S3 survives, so a later run skips weights staging in previous steps.
