# Llama 4 Maverick FP8 with an FP8 KV cache on p6-b200.48xlarge, tensor parallel 8, FlashInfer attention, expert parallel

Serves the published FP8 checkpoint of [`meta-llama/Llama-4-Maverick-17B-128E-Instruct-FP8`](https://huggingface.co/meta-llama/Llama-4-Maverick-17B-128E-Instruct-FP8) as one copy split across all eight GPUs of a p6-b200.48xlarge, using [`fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer-ep.yaml`](../../../vllm-recipes/llama4-maverick/fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer-ep.yaml). This arm adds `--enable-expert-parallel` and changes nothing else from the [FlashInfer baseline](./fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer-runbook.md), so the two are an expert-parallel-vs-tensor-parallel A/B. Read them side by side.

## Capacity sizing

Llama 4 Maverick is a mixture-of-experts model with 128 routed experts. Tensor parallelism alone replicates the router and splits every expert's matrices across the eight GPUs; expert parallelism instead places whole experts on different ranks, so each GPU holds fewer experts and the all-to-all that routes tokens replaces part of the per-layer all-reduce. Whether that wins is the measurement. Enabling it can change the KV pool, so re-read `KV capacity from` and `KV full-ctx seqs` in the result file's provenance block rather than assuming the baseline's allocation.

`coding_repo_context` sends about 14.4k wire input tokens and asks for up to 1,024 output tokens, so a request occupies under half a full-length sequence. The 256-sequence cap, not KV memory, bounds the batch for this workload.

## Before you begin

Create the following in the namespace you deploy into. Secrets and ConfigMaps are namespaced.

- [Create an EKS cluster with Karpenter](../../../scripts/create-cluster.sh) (sets the discovery tags and node role that these steps rely on)
- [Purchase a p6-b200.48xlarge Capacity Block for ML](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-blocks.html) (B200 is not available on demand; note the reservation id for subsequent steps)
- [Accept the Llama 4 license on Hugging Face](https://huggingface.co/meta-llama/Llama-4-Maverick-17B-128E-Instruct-FP8) (only if the checkpoint is not in S3 yet)

## Quickstart

1. Set environment variables.
   ```bash
   export AWS_REGION=<your-cluster-region>
   export EKS_CLUSTER_NAME=<your-cluster-name>
   export HUGGING_FACE_HUB_TOKEN=<your-hf-token>
   export NAMESPACE=vb-llama4-maverick-fp8kv-32k-flashinfer-ep-p6-b200-48xlarge
   export INSTANCE_TYPE=p6-b200.48xlarge
   export RESERVATION_ID=<your-capacity-block-id>
   ```

2. Install the `eks-bench` CLI into a Python virtual environment.
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -e '.[tokenizer]'
   ```

3. Configure the EKS context and namespace, install the NVIDIA device plugin, create the `hf-token` secret, and grant ECR push permissions.
   ```bash
   ./scripts/install-prerequisites.sh
   ```

4. Provision a Capacity Block GPU node pool with NVMe RAID0 for the instance type.
   ```bash
   ./scripts/provision-capacity-block.sh "$INSTANCE_TYPE" "$RESERVATION_ID"
   ```

5. Install the Pod Identity Agent and grant the `llama4-maverick-bench` ServiceAccount S3 access.
   ```bash
   ./scripts/setup-pod-identity.sh llama4-maverick-bench
   ```

6. Copy the published checkpoint from Hugging Face to your S3 bucket.
   ```bash
   ./model-jobs/llama4-maverick/fp8-model-download.sh
   ```

## Throughput test

1. Deploy the inference server and confirm it serves the model.
   ```bash
   ./vllm-recipes/llama4-maverick/fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer-ep-deploy.sh
   ```

2. Confirm `/models` is on the NVMe RAID0 array, not the EBS root volume.
   ```bash
   kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" exec deployment/llama4-maverick-vllm-b200-fp8kv-32k-flashinfer-ep \
       --container vllm -- df -h /models
   ```

3. Generate the accuracy gate (.JSON) that the benchmark checks against.
   ```bash
   eks-bench capture-reference \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service llama4-maverick-vllm-b200-fp8kv-32k-flashinfer-ep \
       --mode fingerprint \
       --model-tag llama4-maverick --config fp8kv-32k-flashinfer-ep \
       --model-id llama4-maverick \
       --out-dir docs/results
   ```

4. Dry-run the exact in-cluster benchmark.
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service llama4-maverick-vllm-b200-fp8kv-32k-flashinfer-ep \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag llama4-maverick \
       --config fp8kv-32k-flashinfer-ep --quant fp8 \
       --model-id llama4-maverick \
       --tokenizer unsloth/Llama-4-Maverick-17B-128E-Instruct-FP8 \
       --out-dir docs/results \
       --reps 3 \
       --dry-run
   ```

5. Run the benchmark in-cluster. If needed, repeat per protocol, changing `--protocol` and `--profile`. For CLI configurations, see [`docs/guides/REFERENCE.md`](../../guides/REFERENCE.md#measure-flags).
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service llama4-maverick-vllm-b200-fp8kv-32k-flashinfer-ep \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag llama4-maverick \
       --config fp8kv-32k-flashinfer-ep --quant fp8 \
       --model-id llama4-maverick \
       --tokenizer unsloth/Llama-4-Maverick-17B-128E-Instruct-FP8 \
       --out-dir docs/results \
       --reps 3
   ```

## Tear down

```bash
kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" delete \
    -f vllm-recipes/llama4-maverick/fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer-ep.yaml --ignore-not-found
kubectl --context "$EKS_CLUSTER_NAME" delete \
    nodepool/bench-cb-p6-b200-48xlarge ec2nodeclass/bench-cb-p6-b200-48xlarge --ignore-not-found
```

Deleting the server leaves the node empty, and Karpenter scales it to zero. The checkpoint in S3 survives, so a later run skips Quickstart step 6.

## Settings

- **`source .venv/bin/activate`** Puts `eks-bench` on your PATH in the current terminal only. If you open a new terminal, run it again from the repository root before continuing.
- **Expert parallelism is the A/B variable.** This arm adds only `--enable-expert-parallel` to the FlashInfer baseline; every other flag is identical, so a throughput or latency difference belongs to expert parallelism. Compare against `...-flashinfer` results under the same profile. The server's provenance block records `expert parallel on`; confirm it before attributing a result.
- **Re-read the KV pool after enabling expert parallelism.** Changing an engine feature can move the KV allocation, so read `KV capacity from` in this run's provenance rather than carrying the baseline's number over.
- **One copy across eight GPUs.** `--tensor-parallel-size 8` spans the node's NVLink mesh, and expert parallelism places whole experts on individual ranks. The server logs `WARNING: no NVLink pairs in topo matrix` at startup if `nvidia-smi topo -m` shows none; do not trust a result from that pod.
- **The backend is pinned with `--attention-backend`, not `VLLM_ATTENTION_BACKEND`.** vLLM 0.29.0 does not read that environment variable and falls back to its auto-selected backend. The deploy script fails unless the server logs `Using AttentionBackendEnum.FLASHINFER backend`.
- **No `--quantization` flag.** The checkpoint's `quantization_config` declares a compressed-tensors FP8 export with dynamic per-token activation scales, and the loader resolves it; pinning the plain `fp8` loader on a foreign export is the failure this avoids. `VLLM_LOGGING_LEVEL=INFO` keeps the resolved method in the server log.
- **`--stream-interval 10`** The server streams in 10-token chunks. That changes inter-token latency only. This arm and the FlashInfer baseline both use 10, so ITL compares between them but never against a recipe with a different stream interval.
- **`--no-enable-prefix-caching`** Held off for an uncached measurement. Confirm `Prefix cache hit` reads 0.0% in the provenance block before publishing any figure.
- **`--async-scheduling` and `--enable-chunked-prefill`.** Both are on in this arm and the baseline, so neither is a variable between them.
- **`MAX_NUM_SEQS=256` and `MAX_CUDAGRAPH=256`.** The batch ceiling and the largest captured CUDA graph match.
- **`MAX_NUM_BATCHED_TOKENS=32768`.** A full `coding_repo_context` prompt prefills in one chunk.
- **The flag surface check.** The server prints `OK` or `ABSENT` for each engine flag the recipe passes, including `--enable-expert-parallel`, before it starts. An `ABSENT` line means the image does not match the recipe.
- **Weights come from S3 into a 900 GiB `emptyDir`, not from a claim.** A pod restart re-downloads ~388 GiB. The `fetch-weights` init container fails unless `/models` has 450 GiB free before the sync and holds 84 shards and at least 360 GiB after it.
- **The free-space check does not prove NVMe placement.** Throughput step 2 confirms `/models` is the RAID0 array; without the RAID0 NodeConfig, the sync lands on EBS.
- **`serviceAccountName: llama4-maverick-bench`** The recipe and the staging Job both run as this ServiceAccount, which EKS Pod Identity binds to an S3 role. One role covers both: S3 write for staging, read for serving. Run `setup-pod-identity.sh llama4-maverick-bench` in this namespace.
- **`--served-model-name llama4-maverick`** The server answers to that name rather than its path, so `--model-id` is `llama4-maverick`.
- **Data-parallel attention is a further test, not part of this A/B.** `--data-parallel-size <N>` is a separate optimization; keep this arm to the single `--enable-expert-parallel` variable so the comparison stays clean.
