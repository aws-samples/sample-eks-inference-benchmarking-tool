# Llama 4 Maverick FP8 with an FP8 KV cache on p6-b200.48xlarge, tensor parallel 8, FlashAttention

Serves the published FP8 checkpoint of [`meta-llama/Llama-4-Maverick-17B-128E-Instruct-FP8`](https://huggingface.co/meta-llama/Llama-4-Maverick-17B-128E-Instruct-FP8) as one copy split across all eight GPUs of a p6-b200.48xlarge, using [`fp8-p6-b200.48xlarge-fp8kv-32k-flashattn.yaml`](../../../vllm-recipes/llama4-maverick/fp8-p6-b200.48xlarge-fp8kv-32k-flashattn.yaml).

## Capacity sizing

Llama 4 Maverick is a mixture-of-experts model, and every expert stays resident, so the ~388 GiB FP8 checkpoint needs the whole node. Its KV cache is light. 8 KV heads at head size 128 across 48 layers cost 96 KiB per token at FP8, so a full 32,768-token sequence holds 3 GiB. At a 0.90 memory fraction, eight 180 GB B200 GPUs leave roughly 820 GiB after the checkpoint, before activations and CUDA graphs. That is room for about 270 full-length sequences, close to the 256-sequence cap. Read `KV capacity from` and `KV full-ctx seqs` in the result file's provenance block for the allocation in force.

`coding_repo_context` sends about 14.4k wire input tokens and asks for up to 1,024 output tokens, so a request occupies under half a full-length sequence. The 256-sequence cap, not KV memory, bounds the batch for this workload.

## Before you begin

Create the following in the namespace you deploy into. Secrets and ConfigMaps are namespaced.

- [Create a `p6-b200.48xlarge` node group](../../../k8s/examples/eksctl-nodegroup-gpu-spot.yaml) (set the instance type)
- [Mount its instance store as RAID0 for kubelet storage](../../../k8s/examples/nodeconfig-local-nvme-raid0.yaml) (the pod stages ~388 GiB)
- [Create a benchmark-client node group](../../../k8s/examples/eksctl-nodegroup-bench-client.yaml) (the client Job does not tolerate the GPU taint)
- [Create an IAM OIDC provider for the cluster](https://docs.aws.amazon.com/eks/latest/userguide/enable-iam-roles-for-service-accounts.html)
- [Create an IAM role for IRSA that reads the S3 checkpoint prefix](https://docs.aws.amazon.com/eks/latest/userguide/associate-service-account-role.html) (add write access if the checkpoint is not in S3 yet)
- [Accept the Llama 4 license on Hugging Face](https://huggingface.co/meta-llama/Llama-4-Maverick-17B-128E-Instruct-FP8) (only if the checkpoint is not in S3 yet)

## Quickstart

1. Set environment variables.
   ```bash
   export AWS_REGION=<your-cluster-region>
   export EKS_CLUSTER_NAME=<your-cluster-name>
   export HUGGING_FACE_HUB_TOKEN=<your-hf-token>
   export NAMESPACE=vb-llama4-maverick-fp8kv-32k-flashattn-p6-b200-48xlarge
   export INSTANCE_TYPE=p6-b200.48xlarge
   export WEIGHTS_BUCKET=<your-weights-bucket>
   export WEIGHTS_REGION=<your-weights-bucket-region>
   export LLAMA4_S3_ROLE_ARN=<your-llama4-maverick-s3-role-arn>
   ```

2. Install the `eks-bench` CLI into a Python virtual environment.
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -e '.[tokenizer]'
   ```

3. Configure the EKS context and namespace, install the NVIDIA device plugin, and create the `hf-token` secret.
   ```bash
   ./scripts/install-prerequisites.sh
   ```

4. Copy the published checkpoint from Hugging Face to your S3 bucket.
   ```bash
   ./model-jobs/llama4-maverick/fp8-model-download.sh
   ```

## Throughput test

1. Deploy the vLLM inference server and confirm it serves the model.
   ```bash
   ./vllm-recipes/llama4-maverick/fp8-p6-b200.48xlarge-fp8kv-32k-flashattn-deploy.sh
   ```

2. Confirm `/models` is on the NVMe RAID0 array, not the EBS root volume.
   ```bash
   kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" exec deployment/llama4-maverick-vllm-b200-fp8kv-32k-flashattn \
       --container vllm -- df -h /models
   ```

3. Generate the accuracy gate (.JSON) that the benchmark checks against.
   ```bash
   eks-bench capture-reference \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service llama4-maverick-vllm-b200-fp8kv-32k-flashattn \
       --mode fingerprint \
       --model-tag llama4-maverick --config fp8kv-32k-flashattn \
       --model-id llama4-maverick \
       --out-dir docs/results
   ```

4. Dry-run the exact in-cluster benchmark.
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service llama4-maverick-vllm-b200-fp8kv-32k-flashattn \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag llama4-maverick \
       --config fp8kv-32k-flashattn --quant fp8 \
       --model-id llama4-maverick \
       --tokenizer unsloth/Llama-4-Maverick-17B-128E-Instruct-FP8 \
       --out-dir docs/results \
       --reps 3 \
       --dry-run
   ```

5. Run the benchmark in-cluster. If needed, repeat per protocol, changing `--protocol` and `--profile`. For CLI configurations, see [`docs/guides/REFERENCE.md`](../../guides/REFERENCE.md#measure-flags).
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service llama4-maverick-vllm-b200-fp8kv-32k-flashattn \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag llama4-maverick \
       --config fp8kv-32k-flashattn --quant fp8 \
       --model-id llama4-maverick \
       --tokenizer unsloth/Llama-4-Maverick-17B-128E-Instruct-FP8 \
       --out-dir docs/results \
       --reps 3
   ```

## Tear down

```bash
kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" delete \
    -f vllm-recipes/llama4-maverick/fp8-p6-b200.48xlarge-fp8kv-32k-flashattn.yaml --ignore-not-found
aws eks update-nodegroup-config --cluster-name "$EKS_CLUSTER_NAME" --nodegroup-name gpu-spot-1node \

```

Scale the benchmark-client node group to zero too if you created it for this run. The checkpoint in S3 survives, so a later run skips Quickstart step 4.

## Settings

- **`source .venv/bin/activate`** Puts `eks-bench` on your PATH in the current terminal only. If you open a new terminal, run it again from the repository root before continuing.
- **One copy across eight GPUs.** All 128 experts stay resident, so `--tensor-parallel-size 8` splits every layer over the node's NVLink mesh. The server logs `WARNING: no NVLink pairs in topo matrix` at startup if `nvidia-smi topo -m` shows none; do not trust a result from that pod.
- **The backend is pinned with `--attention-backend`, not `VLLM_ATTENTION_BACKEND`.** vLLM 0.29.0 does not read that environment variable and falls back to its auto-selected backend. The deploy script fails unless the server logs `Using AttentionBackendEnum.FLASH_ATTN backend`.
- **Why `FLASH_ATTN`.** On B200 this build selects FlashAttention 4, which accepts an FP8 KV cache at head size 128.
- **No `--quantization` flag.** The checkpoint's `quantization_config` declares a compressed-tensors FP8 export with dynamic per-token activation scales, and the loader resolves it; pinning the plain `fp8` loader on a foreign export is the failure this avoids. `VLLM_LOGGING_LEVEL=INFO` keeps the resolved method in the server log. The deploy script asserts only on the backend, so read the method there.
- **`--stream-interval 10`** The server streams in 10-token chunks. That changes inter-token latency only. All three backend arms use 10, so ITL compares within the set but never against a recipe with a different stream interval.
- **`--no-enable-prefix-caching`** Held off for an uncached measurement. Confirm `Prefix cache hit` reads 0.0% in the provenance block before publishing any figure.
- **`--async-scheduling` and `--enable-chunked-prefill`.** Both are on in all three arms, so neither is a variable between them.
- **`MAX_NUM_SEQS=256` and `MAX_CUDAGRAPH=256`.** The batch ceiling and the largest captured CUDA graph match. The pool would allow roughly 270 full-length sequences, and more at this workload's length.
- **`MAX_NUM_BATCHED_TOKENS=32768`.** A full `coding_repo_context` prompt prefills in one chunk.
- **The flag surface check.** The server prints `OK` or `ABSENT` for each engine flag the recipe passes before it starts. An `ABSENT` line means the image does not match the recipe.
- **Weights come from S3 into a 900 GiB `emptyDir`, not from a claim.** A pod restart re-downloads ~388 GiB. The `fetch-weights` init container fails unless `/models` has 450 GiB free before the sync and holds 84 shards and at least 360 GiB after it.
- **The free-space check does not prove NVMe placement.** The example node group's 1,600 GiB EBS root volume also passes it. Throughput step 2 confirms `/models` is the RAID0 array; without the RAID0 NodeConfig, the sync lands on EBS.
- **`serviceAccountName: llama4-maverick-bench`** The recipe and the staging Job both run as this ServiceAccount. The staging Job header calls for IRSA and the recipe names no mechanism, so the staging and deploy scripts annotate it for IRSA. One role covers both: S3 write for staging, read for serving. Node roles on clusters with an IMDS hop limit of 1 are unreachable from pods.
- **The IRSA trust policy names the namespace.** Each arm's runbook uses its own `NAMESPACE`, so a role shared across the three arms must trust `system:serviceaccount:<namespace>:llama4-maverick-bench` for each one.
- **One vLLM pod per namespace.** `measure` auto-discovers the single serving pod for provenance. Pass `--pod` explicitly if you deploy two arms into one namespace.
- **`WEIGHTS_BUCKET` and `AWS_REGION` are placeholders in git.** The staging and deploy scripts fill them in from `WEIGHTS_BUCKET` and `WEIGHTS_REGION` as they apply each manifest, so the files in git stay untouched.
- **The staging Job reads a gated repository.** The `hf-token` must belong to an account that accepted the Llama 4 license. Otherwise set the Job's `MODEL_REPO` to `unsloth/Llama-4-Maverick-17B-128E-Instruct-FP8`, which the Job records as carrying the same shards.
- **The staging Job tolerates the GPU taint.** It requests 400 GiB of ephemeral storage, which rules out typical system CPU nodes, so it can schedule onto the GPU node's instance store.
- **`--tokenizer unsloth/Llama-4-Maverick-17B-128E-Instruct-FP8`** Token counting runs on your machine, and the ungated mirror needs no license acceptance there. The gated `meta-llama` repository works too if your Hugging Face login accepted the license.
- **`--served-model-name llama4-maverick`** The server answers to that name rather than its path, so `--model-id` is `llama4-maverick`.
- **Not comparable to a Hopper run.** FP8 GEMM is native on Blackwell as on Hopper, so the kernel class is the same, but results are labelled with the instance.
