# Mistral Large 3 FP8 on p6-b200.48xlarge, tensor parallel 8, FlashInfer MLA

Serves the published FP8 checkpoint of [`mistralai/Mistral-Large-3-675B-Instruct-2512`](https://huggingface.co/mistralai/Mistral-Large-3-675B-Instruct-2512) as one copy split across all eight B200 GPUs of a p6-b200.48xlarge, using [`fp8-p6-b200.48xlarge.yaml`](../../../vllm-recipes/mistral-large-3/fp8-p6-b200.48xlarge.yaml).

## Capacity sizing

Mistral Large 3 is a mixture-of-experts model with multi-head latent attention (MLA). Every expert stays resident, so the ~635 GiB FP8 checkpoint needs the whole node: about 79 GiB of weights on each 180 GB B200. MLA caches one 576-element latent per token per layer instead of full keys and values, which is 576 bytes at FP8, or about 34.3 KiB per token across 61 layers. Under tensor parallelism every GPU holds the full latent cache. The B200's larger memory leaves more room for KV than the H200 at the same memory fraction. Read `GPU KV cache size` in the server log for the allocation in force.

`chat_typical` sends about 1,245 wire input tokens and asks for up to 1,024 output tokens, so a request occupies about 2,300 tokens. At FP8 the latent cache holds well over 256 such requests, so the 256-sequence cap bounds the batch for this workload.

| Property | Value | Source |
|---|---|---|
| **Parameters** | 675B total, ~41B active per token; 128 routed experts, 4 active, 1 shared; first 3 layers dense | `params.json`, `moe` |
| **Layers** | 61 | `params.json`, `n_layers` |
| **MLA latent per token per layer** | 512 + 64 = 576 elements | `params.json`, `kv_lora_rank` + `qk_rope_head_dim` |
| **KV cache per token, FP8** | ~34.3 KiB, replicated on every GPU | `576 x 1 byte x 61 layers` |
| **Checkpoint size, FP8** | ~635 GiB, 272 `consolidated-*.safetensors` shards | `fetch-weights` init container checks |
| **Instance** | p6-b200.48xlarge, 8x B200 at 180 GB, sm_100, NVLink | `nvidia.com/gpu: "8"` |
| **Tensor parallel size** | 8 | `--tensor-parallel-size 8` |
| **Weight precision** | FP8, compressed-tensors export, block-scaled | `params.json` `quantization_config`; no `--quantization` flag |
| **KV cache precision** | FP8 | `KV_CACHE_DTYPE` |
| **Attention backend** | `FLASHINFER_MLA` | `ATTENTION_BACKEND` |

| **Max batched tokens** | 32,768 | `MAX_NUM_BATCHED_TOKENS` |

## Before you begin

Complete the following tasks before you perform the steps in this runbook.

- [Create an EKS cluster with Karpenter](../../../scripts/create-cluster.sh) (sets the discovery tags and node role that these steps rely on)
- [Purchase a p6-b200.48xlarge Capacity Block for ML](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-blocks.html) (B200 is not available on demand; note its reservation id for Quickstart step 4)

## Quickstart

1. Set environment variables.
   ```bash
   export AWS_REGION=<your-cluster-region>
   export EKS_CLUSTER_NAME=<your-cluster-name>
   export HUGGING_FACE_HUB_TOKEN=<your-hf-token>
   export NAMESPACE=vb-mistral-large-3-fp8-p6-b200-48xlarge
   export INSTANCE_TYPE=p6-b200.48xlarge
   export RESERVATION_ID=<your-capacity-block-id>
   ```

2. Install the `eks-bench` CLI into a Python virtual environment.
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -e '.[tokenizer]'
   ```

3. Configure the EKS context and namespace, install the NVIDIA device plugin, create the `hf-token` secret, and grant ECR push permissions.
   ```bash
   ./scripts/install-prerequisites.sh
   ```

4. Provision a Capacity Block GPU node pool with NVMe RAID0 for the instance type.
   ```bash
   ./scripts/provision-capacity-block.sh "$INSTANCE_TYPE" "$RESERVATION_ID"
   ```

5. Install the Pod Identity Agent and grant the `mistral-large-3-bench` ServiceAccount S3 access.
   ```bash
   ./scripts/setup-pod-identity.sh mistral-large-3-bench
   ```

6. Copy the published checkpoint from Hugging Face to your S3 bucket.
   ```bash
   ./model-jobs/mistral-large-3/fp8-model-download.sh
   ```

## Throughput test

1. Deploy the vLLM inference server and confirm it serves the model.
   ```bash
   ./vllm-recipes/mistral-large-3/fp8-p6-b200.48xlarge-deploy.sh
   ```

2. Confirm `/models` is on the NVMe RAID0 array, not the EBS root volume.
   ```bash
   kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" exec deployment/mistral-large-3-vllm-b200 \
       --container vllm -- df -h /models
   ```

3. Generate the accuracy gate (.JSON) that the benchmark checks against.
   ```bash
   eks-bench capture-reference \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service mistral-large-3-vllm-b200 \
       --mode fingerprint \
       --model-tag mistral-large-3 --config fp8 \
       --model-id mistral-large-3 \
       --out-dir docs/results
   ```

4. Dry-run the exact in-cluster benchmark.
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service mistral-large-3-vllm-b200 \
       --protocol corpus --profile chat_typical \
       --instance p6-b200.48xlarge --model-tag mistral-large-3 \
       --config fp8 --quant fp8 \
       --model-id mistral-large-3 \
       --tokenizer mistralai/Mistral-Large-3-675B-Instruct-2512 \
       --out-dir docs/results \
       --reps 1 \
       --dry-run
   ```

5. Run the benchmark in-cluster. If needed, repeat per protocol, changing `--protocol` and `--profile`. For CLI configurations, see [`docs/guides/REFERENCE.md`](../../guides/REFERENCE.md#measure-flags).
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service mistral-large-3-vllm-b200 \
       --protocol corpus --profile chat_typical \
       --instance p6-b200.48xlarge --model-tag mistral-large-3 \
       --config fp8 --quant fp8 \
       --model-id mistral-large-3 \
       --tokenizer mistralai/Mistral-Large-3-675B-Instruct-2512 \
       --out-dir docs/results \
       --reps 1
   ```

## Tear down

```bash
kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" delete \
    -f vllm-recipes/mistral-large-3/fp8-p6-b200.48xlarge.yaml --ignore-not-found
kubectl --context "$EKS_CLUSTER_NAME" delete \
    nodepool/bench-cb-p6-b200-48xlarge ec2nodeclass/bench-cb-p6-b200-48xlarge --ignore-not-found
```

Deleting the server leaves the node empty, and Karpenter scales it to zero. The checkpoint in S3 survives, so a later run skips Quickstart step 6.

## Settings

- **`source .venv/bin/activate`** Puts `eks-bench` on your PATH in the current terminal only. If you open a new terminal, run it again from the repository root before continuing.
- **One copy across eight GPUs.** All experts stay resident, so `--tensor-parallel-size 8` splits every layer over the node's NVLink mesh. The server logs `WARNING: no NVLink pairs in topo matrix` at startup if `nvidia-smi topo -m` shows none; do not trust a result from that pod.
- **`FLASHINFER_MLA` is a Blackwell MLA backend.** It fails on sm_90 (the H200 recipe used `FLASH_ATTN_MLA` instead), so it has not run on Hopper here. The deploy script fails unless the server logs `Using AttentionBackendEnum.FLASHINFER_MLA backend`. If it does not load on your image, `CUTLASS_MLA` and `FLASHMLA` are the other Blackwell MLA backends to try; set `ATTENTION_BACKEND` and the deploy script's grep to match.
- **The backend is pinned with `--attention-backend`, not `VLLM_ATTENTION_BACKEND`.** vLLM 0.29.0 does not read that environment variable.
- **`--tokenizer-mode mistral --config-format mistral --load-format mistral`.** The checkpoint ships `params.json`, `tekken.json` and `consolidated-*.safetensors` shards, with no Hugging Face `config.json`.
- **No `--quantization` flag.** `params.json` declares a compressed-tensors FP8 export with block scales, and the loader resolves it. `VLLM_LOGGING_LEVEL=INFO` keeps the selected FP8 kernel in the server log.
- **FP8 KV cache.** `KV_CACHE_DTYPE=fp8` stores the cache in FP8. The checkpoint ships no KV-cache scales (`kv_cache_scheme` is null) and vLLM 0.29.0 does not accept `--calculate-kv-scales`, so the scales are uncalibrated (factor 1.0).
- **`PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`** Reclaims fragmented allocator memory so the FP8 MoE warm-up and CUDA-graph capture do not OOM at `GPU_MEM_UTIL=0.85`.
- **`--no-enable-prefix-caching`** Held off for an uncached measurement. Confirm `Prefix cache hit` reads 0.0% in the provenance block before publishing any figure.
- **`--stream-interval 10`** The server streams in 10-token chunks. That changes inter-token latency only, so compare ITL only against recipes with the same stream interval.
- **B200 is Capacity Block only.** p6-b200.48xlarge is not available on demand, so Quickstart step 4 uses `provision-capacity-block.sh` with your reservation id rather than `provision-capacity.sh`.
- **Weights come from S3 into a 1,000 GiB `emptyDir`, not from a claim.** A pod restart re-downloads ~635 GiB. The `fetch-weights` init container fails unless `/models` has 700 GiB free before the sync and holds 272 shards and at least 600 GiB after it.
- **The free-space check does not prove NVMe placement.** The example node group's EBS root volume also passes it. Throughput step 2 confirms `/models` is the RAID0 array; without `instanceStorePolicy: RAID0` on the node pool, the sync lands on EBS.
- **`serviceAccountName: mistral-large-3-bench`** The recipe and the staging Job both run as this ServiceAccount, which the staging and deploy scripts create. Quickstart step 5 creates the IAM role `<cluster>-mistral-large-3-bench-s3` with read and write on `mistral-large-3-model-weights-<account-id>-<region>` only, and associates it with the ServiceAccount through Pod Identity.
- **The weights bucket is `mistral-large-3-model-weights-<account-id>-<region>`.** The staging script creates it in `AWS_REGION` if it does not exist. The staging and deploy scripts fill the bucket name and `AWS_REGION` into each manifest as they apply it, so the files in git stay untouched.
- **`--served-model-name mistral-large-3`** The server answers to that name rather than its path, so `--model-id` is `mistral-large-3`.
- **The chat template adds about 600 tokens.** Mistral's system prompt is part of every request, so `chat_typical` measures about 1,245 wire input tokens against a nominal 512.
- **`--reps 1`** One repetition, so the result has no spread to check. Raise `--reps` before quoting a figure.
- **Not comparable to the H200 run.** Results are labelled with the instance.
