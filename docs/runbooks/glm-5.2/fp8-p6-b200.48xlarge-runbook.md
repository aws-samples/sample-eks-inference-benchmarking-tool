# GLM-5.2 FP8 on p6-b200.48xlarge

Serves [`zai-org/GLM-5.2-FP8`](https://huggingface.co/zai-org/GLM-5.2-FP8) on p6-b200.48xlarge (8x B200, sm_100) with 8 GPUs per pod.

## Capacity sizing

GLM-5.2-FP8 at FP8 occupies 703.7 GiB of the 1,341.1 GiB on 8 B200 cards. The KV pool is 61.35 GiB **per rank**, not the 490.8 GiB you get by summing all eight, because multi-head latent attention replicates the latent cache on every tensor-parallel rank instead of sharding it. At the recipe's 32,768 token context that pool holds 42 concurrent sequences. Measured 2026-08-20, see the note below the table.

| Property | Value | Source |
|---|---|---|
| **Parameters** | 753B total | `zai-org/GLM-5.2-FP8` card; the NVFP4 card reports packed bytes, not parameters |
| **Layers** | 78 | `config.json`, `num_hidden_layers` |
| **KV latent per layer** | kv_lora_rank 512 plus qk_rope 64 | `config.json` |
| **Checkpoint size, FP8** | 703.7 GiB | Model card safetensors metadata |
| **Instance** | p6-b200.48xlarge, 8x B200 at 180 GB | 1,440 GB nominal, 1,341.1 GiB |
| **Tensor parallel size** | 8 | `TP_SIZE` |
| **Weight precision** | FP8 | declared by the checkpoint's `quantization_config` |
| **KV cache precision** | FP8 (`fp8_e4m3`) | `--kv-cache-dtype fp8_e4m3` |
| **Context length** | 32,768 | `MAX_MODEL_LEN` |
| **Memory fraction** | 0.90 | `GPU_MEM_UTIL` |
| **Max sequences** | 512 | `MAX_NUM_SEQS` |

KV cache per layer per token is `(kv_lora_rank + qk_rope_head_dim) x bytes_per_element`, which is 0.56 KiB here, or 43.875 KiB across all 78 layers. Multi-head latent attention caches one compressed latent per layer instead of a key and value per head, so KV cost scales with layer count rather than head count.

That same property is why the pool must not be summed across ranks. A latent cache cannot be split across attention heads, so under tensor parallelism every rank holds a full copy and the usable pool is one rank's share. Summing gives 490.8 GiB and an answer eight times too large.

| Context per request | KV per sequence, per rank | Concurrent sequences |
|---|---|---|
| 4,096 tokens | 0.17 GiB | 337 |
| 8,192 tokens | 0.34 GiB | 168 |
| 32,768 tokens, this recipe's maximum | 1.37 GiB | 42 |

Derived from the 1,380,864-token pool this server actually allocated, divided by the context length. The deploy helper prints the live cache configuration on your hardware, and that value is the one to record. An earlier version of this table summed the pool across all eight ranks and published 2,893, 1,446 and 361, which overstates capacity by the tensor parallel factor.

## Before you begin

Create the following in the namespace you deploy into. Secrets and ConfigMaps are namespaced.

- [Create a `p6-b200.48xlarge` node group](../../../k8s/examples/eksctl-nodegroup-gpu-spot.yaml)
- [Install the FSx CSI driver and create the `fsx-pvc` claim](../../../k8s/examples/README.md#creating-the-weights-filesystem) (nothing mounts without the driver)

## Quickstart

1. Set environment variables.

   ```bash
   export AWS_REGION=<your-cluster-region>
   export EKS_CLUSTER_NAME=<your-cluster-name>
   export HUGGING_FACE_HUB_TOKEN=<your-hf-token>
   export NAMESPACE=vb-glm-52-fp8-p6-b200-48xlarge
   export INSTANCE_TYPE=p6-b200.48xlarge
   ```

2. Install the `eks-bench` CLI into a Python virtual environment.
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -e '.[tokenizer]'
   ```

3. Configure the EKS context and namespace, install the NVIDIA device plugin, and create the `hf-token` secret.

   ```bash
   ./scripts/install-prerequisites.sh
   ```

4. Download the published checkpoint from Hugging Face to the `fsx-pvc` claim.
   ```bash
   ./model-jobs/glm-5.2/fp8-model-download.sh
   ```

5. Deploy the vLLM inference server and confirm it serves the model.

   ```bash
   ./vllm-recipes/glm-5.2/fp8-p6-b200.48xlarge-deploy.sh
   ```

6. Generate the accuracy gate (.JSON) that the benchmark checks against.

   ```bash
   eks-bench capture-reference \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" --service glm-52-b200 \
       --mode fingerprint \
       --model-tag glm-5.2 --config fp8 \
       --model-id glm-5.2-fp8 \
       --thinking off \
       --out-dir docs/results
   ```

7. Dry-run the exact in-cluster benchmark.

   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" --service glm-52-b200 \
       --protocol corpus --profile legacy_corpus \
       --instance p6-b200.48xlarge --model-tag glm-5.2 \
       --config fp8 --quant fp8 \
       --model-id glm-5.2-fp8 \
       --tokenizer nvidia/GLM-5.2-NVFP4 \
       --thinking off \
       --out-dir docs/results \
       --reps 3 \
       --dry-run
   ```

8. Run the benchmark in-cluster. If needed, repeat per protocol, changing `--protocol` and `--profile`. For CLI configurations, see [`docs/guides/REFERENCE.md`](../../guides/REFERENCE.md#measure-flags).

   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" --service glm-52-b200 \
       --protocol corpus --profile legacy_corpus \
       --instance p6-b200.48xlarge --model-tag glm-5.2 \
       --config fp8 --quant fp8 \
       --model-id glm-5.2-fp8 \
       --tokenizer nvidia/GLM-5.2-NVFP4 \
       --thinking off \
       --out-dir docs/results \
       --reps 3
   ```

## Tear down

```bash
kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" delete -f vllm-recipes/glm-5.2/fp8-p6-b200.48xlarge.yaml
```

## Settings

- **`source .venv/bin/activate`** Puts `eks-bench` on your PATH in the current terminal only. If you open a new terminal, run it again from the repository root before continuing.
- **The checkpoint stays on the claim.** A later run can skip Quickstart step 4.
- **`tolerations:`** The shared cluster's GPU nodes carry three NoSchedule taints.

- **`WANT=$(grep -o 'model-[0-9]\{5\}-of-[0-9]\{5\}' "$D/model.safetensors.index.json" | sort -u | wc -l)`** Refuse to start on a partial download: a truncated checkpoint fails in confusing ways deep inside the loader.

- **`--tensor-parallel-size 8`** --- parallelism: 8 GPUs on one node -------------------------------

**`--kv-cache-dtype fp8_e4m3`**

--- precision ---------------------------------------------------- Weights are FP8 in the checkpoint; vLLM auto-detects that, so no

```
--quantization flag. fp8 KV roughly halves the KV budget, which is
```

what makes long context affordable here.

- **`--reasoning-parser glm45`** --- GLM-specific parsers (names per vLLM's GLM-5.2 recipe) --------

- **`--max-model-len 32768`** --- capacity ----------------------------------------------------- 32768 rather than the native 1M: the benchmark protocols use short prompts, and a 1M window would spend the whole KV budget on context instead of on the 512 concurrent sequences the sweep needs.

- **`--max-cudagraph-capture-size 512`** MUST be >= --max-num-seqs. See the note at the top of this file.

- **`--no-enable-prefix-caching`** --- measurement hygiene ------------------------------------------ Prefix caching off: an honest baseline, and vLLM's recipe asks for it when benchmarking.

- **`- name: VLLM_DEEP_GEMM_WARMUP`** Skip DeepGEMM JIT warmup for faster startup. Harmless when deep_gemm is absent, which it is in this image.

- **`startupProbe:`** Loading 704 GiB takes many minutes; a short startup probe would kill the pod mid-load and loop forever.

- **`--thinking off` on the accuracy gate**  Required for this model, and the run fails without it. GLM-5.2 emits a reasoning trace, the fingerprint tier caps output at 256 tokens, and the trace consumes the whole budget: 18 of 20 problems come back with empty content and `finish_reason=length`, and the gate refuses to write a reference from what looks like a broken server. The flag reaches `accuracy.py` through `measure`'s unknown-argument passthrough, so it does not appear in `measure --help` but is forwarded correctly. Suppressing the trace is right for the gate specifically, which is asking whether the server is configured as claimed, not whether the model can reason. Benchmark the reasoning behaviour with `--protocol reasoning` instead, which budgets 1024 output tokens and counts reasoning tokens in the total.

- **`--protocol corpus` on a cold server**  Corpus pins `WARMUP_REQUESTS=0`, so the first rep pays first-touch and JIT cost at every concurrency level, and with `VLLM_DEEP_GEMM_WARMUP=skip` set above there is no startup warmup either. Measured on this recipe: a 3-rep run straight after rollout reported 1,615.9 output tok/s at concurrency 128 against 4,604.6 for the same sweep on a warm server, understating it by 2.85x, while every request succeeded and the accuracy gate passed. Concurrency 1 and 8 were unaffected, because those levels run long enough to amortise the cost. Either discard the first sweep as a warmup pass and quote the second, or raise the rep count and believe only the cells the harness does not flag. Do not change the protocol's warmup default to fix this: corpus exists for continuity with historical results, and warming it would silently redefine what those results mean.
