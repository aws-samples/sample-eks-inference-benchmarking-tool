# Gemma 4 31B FP8 with an FP8 KV cache on p6-b200.48xlarge, eight text-only replicas, FlashInfer attention

Serves a locally quantized ModelOpt FP8 build of [`google/gemma-4-31b-it`](https://huggingface.co/google/gemma-4-31b-it) as eight independent single-GPU replicas behind one Service, using [`fp8-p6-b200.48xlarge-fp8kv-32k-dp8-textonly-flashinfer.yaml`](../../../vllm-recipes/gemma4-31b/fp8-p6-b200.48xlarge-fp8kv-32k-dp8-textonly-flashinfer.yaml). Each replica runs with `--language-model-only`, which lets the engine accept `FLASHINFER` for this model.

## Capacity sizing

Gemma 4 31B carries a heavy KV cache for its size. The recipe sizes it at about 480 KiB per token at FP8, so a ~21k-token `coding_repo_context` request takes about 10 GiB. The 30.4 GiB checkpoint fits one 180 GB B200 with room for about 14 such requests, which is why each replica takes one GPU and `MAX_NUM_SEQS=16` caps just above that. Read `KV capacity from` and `KV full-ctx seqs` in the result file's provenance block for the allocation in force.

`coding_repo_context` sends about 20.3k wire input tokens with this tokenizer and asks for up to 1,024 output tokens.

| Property | Value | Source |
|---|---|---|
| **Parameters** | 31B dense | Model card |
| **Layers** | 60, of which 10 full attention and 50 sliding at window 1024 | `config.json`, `text_config.layer_types` |
| **KV heads, head dimension** | 16, 256 | `config.json` |
| **KV cache per token, FP8** | ~480 KiB as sized by the recipe | `MAX_NUM_SEQS` comment |
| **Checkpoint size, FP8** | 30.4 GiB | `fetch-weights` checks at least 25 GiB |
| **Instance** | p6-b200.48xlarge, 8x B200 at 180 GB, sm_100 | Instance type |
| **Serving layout** | 8 replicas x 1 GPU, one Service | `replicas: 8`, `nvidia.com/gpu: "1"` |
| **Weight precision** | FP8 E4M3, ModelOpt export | `QUANTIZATION` |
| **KV cache precision** | FP8 E4M3, uncalibrated scales | `KV_CACHE_DTYPE`; see Settings |
| **Attention backend** | `FLASHINFER` | `ATTENTION_BACKEND` |
| **Modality** | Text only | `--language-model-only` |
| **Context length** | 32,768 | `MAX_MODEL_LEN` |
| **Max sequences** | 16 per replica | `MAX_NUM_SEQS` |
| **Memory fraction** | 0.90 | `GPU_MEM_UTIL` |
| **Stream interval** | 10 tokens | `STREAM_INTERVAL` |

## Before you begin

Complete the following tasks before you perform the steps in this runbook.

- [Create an EKS cluster with Karpenter, Karpenter discovery tags and node role](../../../scripts/create-cluster.sh)
- [Purchase a p6-b200.48xlarge Capacity Block for ML](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/ec2-capacity-blocks.html)
- [Install the FSx CSI driver and create the `fsx-pvc` claim](../../../k8s/examples/README.md#creating-the-weights-filesystem)

## Quickstart

1. Set environment variables.
   ```bash
   export AWS_REGION=<your-cluster-region>
   export AWS_ACCOUNT_ID=<your-account-id>
   export EKS_CLUSTER_NAME=<your-cluster-name>
   export HUGGING_FACE_HUB_TOKEN=<your-hf-token>
   export NAMESPACE=vb-gemma4-31b-fp8kv-32k-dp8-textonly-flashinfer-p6-b200-48xlarge
   export INSTANCE_TYPE=p6-b200.48xlarge
   export RESERVATION_ID=<your-capacity-block-id>
   ```

2. Install the `eks-bench` CLI into a Python virtual environment.
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -e '.[tokenizer]'
   ```

3. Configure the EKS context and namespace, install the NVIDIA device plugin, create the `hf-token` secret, and grant ECR push permissions.
   ```bash
   ./scripts/install-prerequisites.sh
   ```

4. Provision a Capacity Block GPU node pool with NVMe RAID0 for the instance type.
   ```bash
   ./scripts/provision-capacity-block.sh "$INSTANCE_TYPE" "$RESERVATION_ID"
   ```

5. Provision an on-demand GPU node pool with NVMe RAID0 for the quantizer.
   ```bash
   ./scripts/provision-capacity.sh g7.24xlarge
   ```

6. Install the Pod Identity Agent and grant the `gemma4-31b-bench` ServiceAccount S3 access.
   ```bash
   ./scripts/setup-pod-identity.sh gemma4-31b-bench
   ```

7. Build the quantizer tool image in-cluster with kaniko, create the ECR repository, and push it. This step takes several minutes to complete. Alternatively, to build locally on x86 Docker, run `./scripts/push-image.sh`.
   ```bash
   ./scripts/push-image-kaniko.sh
   ```

8. Quantize the model to ModelOpt FP8 and save the checkpoint to the `fsx-pvc` claim.
   ```bash
   ./model-jobs/gemma4-31b/fp8-model-quantize.sh
   ```

9. Copy the quantized checkpoint from the claim to your S3 bucket.
   ```bash
   ./model-jobs/gemma4-31b/fp8-model-fsx-to-s3.sh
   ```

## Throughput test

1. Deploy eight vLLM inference server replicas and confirm they serve the model.
   ```bash
   ./vllm-recipes/gemma4-31b/fp8-p6-b200.48xlarge-fp8kv-32k-dp8-textonly-flashinfer-deploy.sh
   ```

2. Generate the accuracy gate (.JSON) that the benchmark checks against.
   ```bash
   eks-bench capture-reference \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service gemma4-31b-vllm-b200-fp8kv-32k-dp8-textonly-flashinfer \
       --mode fingerprint \
       --model-tag gemma4-31b --config fp8kv-32k-dp8-textonly-flashinfer \
       --model-id gemma4-31b \
       --out-dir docs/results
   ```

3. Dry-run the exact in-cluster benchmark.
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service gemma4-31b-vllm-b200-fp8kv-32k-dp8-textonly-flashinfer \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag gemma4-31b \
       --config fp8kv-32k-dp8-textonly-flashinfer --quant fp8 \
       --model-id gemma4-31b \
       --tokenizer google/gemma-4-31b-it \
       --pod "$(kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" get pods \
           -l app=gemma4-31b-vllm-b200-fp8kv-32k-dp8-textonly-flashinfer -o jsonpath='{.items[0].metadata.name}')" \
       --out-dir docs/results \
       --reps 3 \
       --dry-run
   ```

4. Run the benchmark in-cluster. If needed, repeat per protocol, changing `--protocol` and `--profile`. For CLI configurations, see [`docs/guides/REFERENCE.md`](../../guides/REFERENCE.md#measure-flags).
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service gemma4-31b-vllm-b200-fp8kv-32k-dp8-textonly-flashinfer \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag gemma4-31b \
       --config fp8kv-32k-dp8-textonly-flashinfer --quant fp8 \
       --model-id gemma4-31b \
       --tokenizer google/gemma-4-31b-it \
       --pod "$(kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" get pods \
           -l app=gemma4-31b-vllm-b200-fp8kv-32k-dp8-textonly-flashinfer -o jsonpath='{.items[0].metadata.name}')" \
       --out-dir docs/results \
       --reps 3
   ```

## Tear down

```bash
kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" delete \
    -f vllm-recipes/gemma4-31b/fp8-p6-b200.48xlarge-fp8kv-32k-dp8-textonly-flashinfer.yaml --ignore-not-found
kubectl --context "$EKS_CLUSTER_NAME" delete \
    nodepool/bench-cb-p6-b200-48xlarge ec2nodeclass/bench-cb-p6-b200-48xlarge --ignore-not-found
kubectl --context "$EKS_CLUSTER_NAME" delete \
    nodepool/bench-g7-24xlarge ec2nodeclass/bench-g7-24xlarge --ignore-not-found
```

Deleting the server leaves the node empty, and Karpenter scales both the serving and quantize pools to zero. The checkpoint in S3 survives, so a later run skips Quickstart steps 5 and 7 to 9.
