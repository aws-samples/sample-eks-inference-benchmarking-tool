# Gemma 4 31B FP8 with an FP8 KV cache on p6-b200.48xlarge, eight text-only replicas, FlashInfer attention

Serves a locally quantized ModelOpt FP8 build of [`google/gemma-4-31b-it`](https://huggingface.co/google/gemma-4-31b-it) as eight independent single-GPU replicas behind one Service, using [`fp8-p6-b200.48xlarge-fp8kv-32k-dp8-textonly-flashinfer.yaml`](../../../vllm-recipes/gemma4-31b/fp8-p6-b200.48xlarge-fp8kv-32k-dp8-textonly-flashinfer.yaml). Each replica runs with `--language-model-only`, which lets the engine accept `FLASHINFER` for this model.

## Capacity sizing

Gemma 4 31B carries a heavy KV cache for its size. The recipe sizes it at about 480 KiB per token at FP8, so a ~21k-token `coding_repo_context` request takes about 10 GiB. The 30.4 GiB checkpoint fits one 180 GB B200 with room for about 14 such requests, which is why each replica takes one GPU and `MAX_NUM_SEQS=16` caps just above that. Read `KV capacity from` and `KV full-ctx seqs` in the result file's provenance block for the allocation in force.

`coding_repo_context` sends about 20.3k wire input tokens with this tokenizer and asks for up to 1,024 output tokens.

## Before you begin

Create the following in the namespace you deploy into. Secrets and ConfigMaps are namespaced.

- [Create a `p6-b200.48xlarge` node group](../../../k8s/examples/eksctl-nodegroup-gpu-spot.yaml) (set the instance type)
- [Mount its instance store as RAID0 for kubelet storage](../../../k8s/examples/nodeconfig-local-nvme-raid0.yaml) (eight replicas stage about 240 GiB)
- [Create a benchmark-client node group](../../../k8s/examples/eksctl-nodegroup-bench-client.yaml) (the client Job does not tolerate the GPU taint)
- [Install the EKS Pod Identity Agent add-on](https://docs.aws.amazon.com/eks/latest/userguide/pod-id-agent-setup.html)
- [Associate an S3 read role with the `gemma4-31b-bench` ServiceAccount in your namespace through Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-id-association.html)
- [Install Docker](https://docs.docker.com/get-started/get-docker/) (builds the quantizer image on your machine)
- [Create a `g7.24xlarge` node group for quantization](../../../k8s/examples/eksctl-nodegroup-gpu-spot.yaml) (only if the checkpoint is not in S3 yet)
- [Install the FSx CSI driver and create the `fsx-pvc` claim](../../../k8s/examples/README.md#creating-the-weights-filesystem) (only if the checkpoint is not in S3 yet)
- [Grant S3 write access to the staging Job](https://docs.aws.amazon.com/eks/latest/userguide/pod-id-association.html) (only if the checkpoint is not in S3 yet)

## Quickstart

1. Set environment variables.
   ```bash
   export AWS_REGION=<your-cluster-region>
   export AWS_ACCOUNT_ID=<your-account-id>
   export EKS_CLUSTER_NAME=<your-cluster-name>
   export HUGGING_FACE_HUB_TOKEN=<your-hf-token>
   export NAMESPACE=vb-gemma4-31b-fp8kv-32k-dp8-textonly-flashinfer-p6-b200-48xlarge
   export INSTANCE_TYPE=p6-b200.48xlarge
   export WEIGHTS_BUCKET=<your-weights-bucket>
   export WEIGHTS_REGION=<your-weights-bucket-region>
   ```

2. Install the `eks-bench` CLI into a Python virtual environment.
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -e '.[tokenizer]'
   ```

3. Configure the EKS context and namespace, install the NVIDIA device plugin, and create the `hf-token` secret.
   ```bash
   ./scripts/install-prerequisites.sh
   ```

4. Build the quantizer image and push it to your ECR repository, creating the repository if needed.
   ```bash
   ./scripts/push-image.sh
   ```

5. Quantize the model to ModelOpt FP8 and save the checkpoint to the `fsx-pvc` claim.
   ```bash
   ./model-jobs/gemma4-31b/fp8-model-quantize.sh
   ```

6. Copy the quantized checkpoint from the claim to your S3 bucket.
   ```bash
   ./model-jobs/gemma4-31b/fp8-model-fsx-to-s3.sh
   ```

## Throughput test

1. Deploy eight vLLM inference server replicas and confirm they serve the model.
   ```bash
   ./vllm-recipes/gemma4-31b/fp8-p6-b200.48xlarge-fp8kv-32k-dp8-textonly-flashinfer-deploy.sh
   ```

2. Generate the accuracy gate (.JSON) that the benchmark checks against.
   ```bash
   eks-bench capture-reference \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service gemma4-31b-vllm-b200-fp8kv-32k-dp8-textonly-flashinfer \
       --mode fingerprint \
       --model-tag gemma4-31b --config fp8kv-32k-dp8-textonly-flashinfer \
       --model-id gemma4-31b \
       --out-dir docs/results
   ```

3. Dry-run the exact in-cluster benchmark.
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service gemma4-31b-vllm-b200-fp8kv-32k-dp8-textonly-flashinfer \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag gemma4-31b \
       --config fp8kv-32k-dp8-textonly-flashinfer --quant fp8 \
       --model-id gemma4-31b \
       --tokenizer google/gemma-4-31b-it \
       --pod "$(kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" get pods \
           -l app=gemma4-31b-vllm-b200-fp8kv-32k-dp8-textonly-flashinfer -o jsonpath='{.items[0].metadata.name}')" \
       --reps 3 --out-dir docs/results \
       --dry-run
   ```

4. Run the benchmark in-cluster. If needed, repeat per protocol, changing `--protocol` and `--profile`.
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service gemma4-31b-vllm-b200-fp8kv-32k-dp8-textonly-flashinfer \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag gemma4-31b \
       --config fp8kv-32k-dp8-textonly-flashinfer --quant fp8 \
       --model-id gemma4-31b \
       --tokenizer google/gemma-4-31b-it \
       --pod "$(kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" get pods \
           -l app=gemma4-31b-vllm-b200-fp8kv-32k-dp8-textonly-flashinfer -o jsonpath='{.items[0].metadata.name}')" \
       --reps 3 --out-dir docs/results
   ```

## Tear down

```bash
kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" delete \
    -f vllm-recipes/gemma4-31b/fp8-p6-b200.48xlarge-fp8kv-32k-dp8-textonly-flashinfer.yaml --ignore-not-found
aws eks update-nodegroup-config --cluster-name "$EKS_CLUSTER_NAME" --nodegroup-name gpu-spot-1node \
    --region "$AWS_REGION" --scaling-config minSize=0,maxSize=1,desiredSize=0
```

Scale the quantization and benchmark-client node groups to zero too if you created them for this run. The checkpoint in S3 survives, so a later run skips Quickstart steps 4 to 6.

## Settings

- **`source .venv/bin/activate`** Puts `eks-bench` on your PATH in the current terminal only. If you open a new terminal, run it again from the repository root before continuing.
- **Eight copies rather than one split copy.** The checkpoint fits one GPU, so each replica owns a B200 and no layer crosses NVLink. One Service balances requests between them.
- **`--language-model-only`** Sets every image and video limit to 0, which turns off vLLM's multimodal prefix attention mode. With it on, the engine refuses `FLASHINFER` for this model with "partial multimodal token full attention not supported". It also skips the vision encoder, freeing memory for KV cache, so never compare this recipe's results with a multimodal configuration.
- **The Service balances per connection, not per request.** The benchmark client holds one persistent connection per in-flight request, so at low concurrency some replicas can sit idle.
- **`--pod` names one replica for provenance.** `measure` reads the image, KV pool and server log from that pod. Every replica runs the same spec.
- **The backend is pinned with `--attention-backend`, not `VLLM_ATTENTION_BACKEND`.** vLLM 0.29.0 does not read that environment variable and falls back to its auto-selected backend. The deploy script fails unless the server logs `Using AttentionBackendEnum.FLASHINFER backend`.
- **`--stream-interval 10`** The server streams in 10-token chunks. That changes inter-token latency only, so never compare ITL against a recipe with a different stream interval, such as the g7.24xlarge one.
- **KV scales are uncalibrated.** vLLM 0.29.0 rejects `--calculate-kv-scales`, so each server logs `Using KV cache scaling factor 1.0 for fp8_e4m3`. This bounds any quality comparison.
- **`--no-enable-prefix-caching`** Held off for an uncached measurement. Confirm `Prefix cache hit` reads 0.0% in the provenance block before publishing any figure.
- **`MAX_NUM_SEQS=16` and `MAX_CUDAGRAPH=16`.** About 14 full `coding_repo_context` requests fit per card, so 16 caps just above the pool.
- **`MAX_NUM_BATCHED_TOKENS=32768`.** A full `coding_repo_context` prompt prefills in one chunk.
- **No `strategy: Recreate`.** The Deployment rolls replicas on a reapply, and a surge pod cannot schedule while all eight GPUs are held. Tear down before redeploying.
- **Weights come from S3 into an `emptyDir`, not from the claim.** Each replica syncs its own copy, so a pod restart re-downloads 30 GiB. The `fetch-weights` init container fails unless it finds `config.json` and at least 25 GiB.
- **`serviceAccountName: gemma4-31b-bench`** Supplies the pod-scoped S3 read identity through EKS Pod Identity. Node roles on clusters with an IMDS hop limit of 1 are unreachable from pods.
- **`WEIGHTS_BUCKET` and `AWS_REGION` are placeholders in git.** The staging and deploy scripts fill them in from `WEIGHTS_BUCKET` and `WEIGHTS_REGION` as they apply each manifest, so the files in git stay untouched.
- **The S3 staging Job sets no ServiceAccount.** It runs as the namespace's `default` ServiceAccount, so that is the identity the write role must be associated with.
- **The quantize Job takes all four g7.24xlarge GPUs.** The BF16 source is about 62 GB, more than one 32 GB card, so `quantize.py` shards the load with `device_map="auto"`. It keeps the vision tower, projector and head in 16-bit.
