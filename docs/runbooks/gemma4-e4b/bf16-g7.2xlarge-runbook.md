# Gemma 4 E4B BF16 on g7.2xlarge

Serves [`google/gemma-4-E4B-it`](https://huggingface.co/google/gemma-4-E4B-it) on g7.2xlarge (1x RTX PRO 4500 Blackwell, sm_120) with 1 GPU per pod. Two recipes share this runbook, differing only in `--max-num-batched-tokens` and `--stream-interval`: [`bf16-g7.2xlarge-throughput.yaml`](../../../vllm-recipes/gemma4-e4b/bf16-g7.2xlarge-throughput.yaml) and [`bf16-g7.2xlarge-latency.yaml`](../../../vllm-recipes/gemma4-e4b/bf16-g7.2xlarge-latency.yaml).

## Capacity sizing

gemma-4-E4B-it at BF16 occupies 14.89 GiB of the 31.9 GiB on 1 RTX PRO 4500 Blackwell card, leaving roughly 16 GiB for KV cache. At the recipe's 8,192 token context that pool holds over 60 concurrent sequences, so KV is never what bounds this deployment; `--max-num-seqs` and compute are. Read `KV capacity from` and `KV full-ctx seqs` in the result file's provenance block for the allocation actually in force.

| Property | Value | Source |
|---|---|---|
| **Parameters** | 4B active, 8B on disk | Model card |
| **Layers** | 42, of which 7 full attention and 35 sliding at window 512 | `config.json`, `text_config.layer_types` |
| **KV-owning layers** | 24; the last 18 share KV with earlier layers | `config.json`, `text_config.num_kv_shared_layers` |
| **KV heads, head dimension** | 2; 256 sliding, 512 full attention | `config.json`, `head_dim` and `global_head_dim` |
| **Checkpoint size, BF16** | 14.89 GiB, one safetensors file | `model.safetensors` blob size |
| **Instance** | g7.2xlarge, 1x RTX PRO 4500 Blackwell at 32 GB | 32 GB nominal, 31.9 GiB |
| **Tensor parallel size** | 1 | unset, single GPU |
| **Weight precision** | BF16 | `DTYPE`, pinned `--dtype bfloat16` |
| **KV cache precision** | BF16, 16-bit | `KV_CACHE_DTYPE=auto`, resolves through `DTYPE`, see Settings |
| **Context length** | 8,192 | `MAX_MODEL_LEN`, model supports 131,072 |
| **Memory fraction** | 0.80 | `GPU_MEM_UTIL` |
| **Max sequences** | 1,024 | `MAX_NUM_SEQS` |

KV cache per layer per token is `2 x kv_heads x head_dim x bytes_per_element`, which is 2 KiB on a sliding layer and 4 KiB on a full attention layer, since the two use different head dimensions. Two properties of E4B make its cache far cheaper than the layer count suggests: the last 18 of 42 layers share KV with earlier layers, so only 24 layers own a cache, and the 20 sliding layers among those hold at most 512 tokens whatever the context length. Only the 4 full attention layers that own a cache grow with context, so one 8,192-token sequence costs 0.145 GiB, against 0.520 GiB at 32,768 and 2.020 GiB at the full 131,072.

## Before you begin

Create the following in the namespace you deploy into. Secrets and ConfigMaps are namespaced.

- [Create a `g7.2xlarge` node group](../../../k8s/examples/eksctl-nodegroup-gpu-spot.yaml) (in a subnet with free IPs; this instance type's AZ may have none by default)
- Give that node group a launch template setting `instance.localStorage.strategy: RAID0` (without it an `emptyDir` lands on the EBS root volume)
- [Apply the `nvidia-open-driver-healer` DaemonSet](../../../k8s/examples/daemonset-nvidia-open-driver.yaml) (without it the node advertises no GPU indefinitely)

No FSx PVC in this runbook. Both recipes download their own weights into an `emptyDir`, the same pattern `gemma4-31b/bf16-g7e.2xlarge.yaml` uses, because no FSx for Lustre filesystem exists in every AZ this instance type's capacity might land in.

## Quickstart

Steps 1 to 3 are shared. Then run the throughput test, the latency test, or both. There is one GPU, so tear down one config before deploying the other.

1. Set environment variables.

   ```bash
   export AWS_REGION=<your-cluster-region>
   export EKS_CLUSTER_NAME=<your-cluster-name>
   export HUGGING_FACE_HUB_TOKEN=<your-hf-token>
   export NAMESPACE=vb-gemma4-e4b-bf16-g7-2xlarge
   export INSTANCE_TYPE=g7.2xlarge
   ```

2. Configure the EKS context and namespace, install the NVIDIA Kubernetes device plugin, and create the `hf-token` secret.

   ```bash
   ./scripts/install-prerequisites.sh
   ```

3. Confirm the sitecustomize ConfigMap exists in the namespace.

   ```bash
   kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" get configmap vllm-sitecustomize
   ```

## Throughput test

1. Deploy and validate the model server. Its init container downloads the weights into pod-local (`emptyDir`) storage before vLLM starts, so the first rollout takes as long as the download and pod replacement downloads them again.

   ```bash
   ./vllm-recipes/gemma4-e4b/bf16-g7.2xlarge-throughput-deploy.sh
   ```

2. Generate the accuracy gate (.JSON) required for the next step.

   ```bash
   eks-bench capture-reference \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" --service gemma4-e4b-vllm-g7-2xl-throughput \
       --mode fingerprint \
       --model-tag gemma4-e4b --config throughput \
       --model-id /models/gemma-4-E4B-it \
       --out-dir docs/results
   ```

3. Dry-run the in-cluster benchmark. This validates and renders the Job without creating cluster resources.

   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" --service gemma4-e4b-vllm-g7-2xl-throughput \
       --protocol corpus --profile chat_terse \
       --instance g7.2xlarge --model-tag gemma4-e4b \
       --config throughput --quant bf16 \
       --model-id /models/gemma-4-E4B-it \
       --tokenizer google/gemma-4-E4B-it \
       --pod "$(kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" get pods \
           -l app=gemma4-e4b-vllm-g7-2xl-throughput -o jsonpath='{.items[0].metadata.name}')" \
       --reps 3 --out-dir docs/results \
       --dry-run
   ```

4. Benchmark in-cluster. If needed, repeat per protocol, changing `--protocol` and `--profile`.

   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" --service gemma4-e4b-vllm-g7-2xl-throughput \
       --protocol corpus --profile chat_terse \
       --instance g7.2xlarge --model-tag gemma4-e4b \
       --config throughput --quant bf16 \
       --model-id /models/gemma-4-E4B-it \
       --tokenizer google/gemma-4-E4B-it \
       --pod "$(kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" get pods \
           -l app=gemma4-e4b-vllm-g7-2xl-throughput -o jsonpath='{.items[0].metadata.name}')" \
   ```

## Settings

- **`--dtype bfloat16`** Pinned rather than inferred from the checkpoint, so the manifest states the precision. Not an arbitrary choice of 16-bit format: Gemma's activations exceed float16's 65,504 ceiling, and vLLM carries an [open defect where Gemma 4 produces garbage under fp16](https://github.com/vllm-project/vllm/issues/40290). Matches the `qwen2.5-7b/bf16-*.yaml` recipes, which pin the same way.

- **`--kv-cache-dtype auto`** MUST be `auto` on this model, which is not a defaulting shortcut. Pinning the literal `bfloat16` passes argument parsing, because it is a member of the `CacheDType` literal, then kills the engine during KV initialisation with `AssertionError: unsupported kv_cache_dtype (str), got bfloat16`. [The CacheConfig documentation](https://docs.vllm.ai/en/v0.21.0/api/vllm/config/cache/) gives the reason: that value is valid only for models whose checkpoint defaults to FP8. The `llama3.3-70b` and `qwen3-30b-a3b` recipes pin it legitimately because they serve FP8 weights; this one serves BF16, so `auto` is the only route to a 16-bit cache and it resolves to BF16 through `--dtype`. Verified on vLLM 0.21.0, 2026-09-12; retest before changing it.

- **No FP8 or NVFP4 KV cache.** This build also accepts `fp8`, `fp8_e4m3`, `fp8_e5m2`, `nvfp4` and several `turboquant` variants. All are declined: at roughly 110 tokens per request this workload uses under a tenth of the KV pool, so halving per-token cost doubles headroom that is already unused and trades accuracy for nothing. FP8 KV earns its place at long context, where it would roughly double the concurrent full-8,192-token sequences.

- **`--max-model-len 8192`** Context capped at 8,192, well below the model's 131,072, so context length is fixed rather than a variable in any measurement. Raising it costs 0.25 GiB of KV per additional 8,192 tokens per sequence, since only the 4 cache-owning full attention layers grow.

- **`--max-num-seqs 1024`** Deliberately above the canonical sweep's top level of 512, in both recipes. Capping it lower would reduce batch contention for admitted requests, but the surplus would queue at the server, and a queued request still returns HTTP 200: `MIN_LEVEL_SUCCESS` stays clean, peak in-flight still reaches the label client-side so the under-fill check does not fire, and the queue wait lands silently in TTFT. The run would look valid and measure its own admission limit. KV supports the higher ceiling with room to spare.

- **`--max-num-batched-tokens`** The one capacity flag that differs: `16384` for throughput, `2048` for latency, following [vLLM's optimization guide](https://docs.vllm.ai/en/v0.25.0/configuration/optimization/), which states smaller values near 2048 give better inter-token latency while higher values give better time-to-first-token. Measured on this workload the two are within noise of each other, because a 96-token prompt never competes for either budget; the documented trade appears when prompts are large enough to fill it, as `coding_assistant` at 8,192 tokens would. Do not carry that null result to a long-prompt profile. The larger buffer does cost KV: about 36,000 tokens of cache, measured like-for-like.

- **`--gpu-memory-utilization 0.80`** Lower than the 0.95 the 31B recipes use, and lower than the usual batch-serving advice, because a 32 GiB card leaves less absolute headroom for activations and CUDA graphs once weights are resident. 0.85 and 0.90 both aborted during CUDA graph capture with `torch.OutOfMemoryError`; 0.80 is retained across versions so the figure is comparable, not because the higher values were retested. Raising it would buy more KV, which this workload does not need.

- **`--stream-interval`** The other flag that differs: `10` for throughput, `1` for latency. At 1 every token is sent as produced, which is what makes the ITL column a per-token measurement. At 10 tokens are batched before sending, cutting host overhead. TPOT is unaffected either way, so **compare ITL only within one config**, never across the two.

- **`--async-scheduling`** Set in both. Documented in this build as avoiding gaps in GPU utilisation for better latency and throughput; off by default.

- **`--scheduling-policy fcfs`** Stated rather than defaulted. `priority` would require per-request priorities that the harness does not send.

- **`--enable-chunked-prefill`** Set in both. In vLLM V1 the scheduler prioritises decode and chunks any prefill that will not fit the token budget, which improves inter-token latency and keeps compute-bound prefill and memory-bound decode in the same batch.

- **`--no-enable-prefix-caching`** Off in both, for measurement hygiene. The pinned profiles cycle a small prompt pool, and a `chat_terse` run with caching on measured a 77.9% prefix cache hit rate, meaning most prefill was skipped and the throughput figure was inflated by roughly a factor of two. Every result file states the rule: a non-zero hit rate means prefill was skipped. Check `Prefix cache hit` in the provenance block of each run; it should read 0.0%. Note that `chat_terse` sets `fixed_prompt_set: false`, so it prints no repeat warning of its own.

- **`fetch-weights` init container** Downloads `google/gemma-4-E4B-it` into the `model-storage` `emptyDir` before vLLM starts. Checks free space against `MIN_FREE_GIB` first, since an `emptyDir` lands wherever kubelet's root is rather than necessarily the instance store. E4B ships one safetensors file rather than a sharded checkpoint, so completeness is checked by that file's presence and the absence of `.incomplete` files rather than by counting shards against an index.

- **`model-storage: emptyDir: {sizeLimit: 60Gi}`** Sized for the 14.89 GiB checkpoint plus the Hugging Face cache under the same mount, with headroom. With the `RAID0` launch template from Before you begin, this lands on the NVMe instance store rather than the EBS root volume. Scaling the deployment to zero discards the download; a re-run downloads again.

- **`nvidia.com/gpu: 1`** g7.2xlarge = 1x Blackwell RTX PRO 4500, 32 GB (sm_120), a third the memory of the RTX PRO 6000 in the g7e family, which is why the memory fraction and batched-token budgets differ from the 31B recipes.

- **Harness values the protocol pins, which exporting cannot change.** `build_env` applies the protocol's environment after the inherited one, so the `corpus` protocol fixes `CONCURRENCY_SWEEP` at the canonical `1,8,32,128,256,512`, `NUM_REQUESTS` at a floor of 100 silently raised to whole waves, `MIN_DURATION_S` at 0 and `WARMUP_REQUESTS` at 0. A profile then overrides `MAX_TOKENS`. Two consequences worth knowing: with no duration floor and a 30-token output cap the top levels run only two waves, so read `ACHIEVED IN-FLIGHT DEPTH` before quoting the 256 and 512 rows; and `stats.percentile` is nearest-rank, so at 100 samples a p99 cell is the single worst sample and `MAX_SPREAD` will often flag it across reps.

- **Quote `req_per_sec`, not `tokens_per_sec`, on this profile.** `tokens_per_sec` counts output tokens only. `chat_terse` puts 96 of its 126 tokens on the input side, so it reads low while the server is doing more work than a long-output profile. To reconcile the two, compute `req_per_sec x (input + output)` using the `MEASURED TOKEN SHAPE` table for the input size; the harness does not print that figure.
