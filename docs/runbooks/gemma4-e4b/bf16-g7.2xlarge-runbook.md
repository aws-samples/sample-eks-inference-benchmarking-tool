# Gemma 4 E4B BF16 on g7.2xlarge

Serves [`google/gemma-4-E4B-it`](https://huggingface.co/google/gemma-4-E4B-it) on g7.2xlarge (1x RTX PRO 4500 Blackwell, sm_120) with 1 GPU per pod.

## Capacity sizing

gemma-4-E4B-it at BF16 occupies 14.89 GiB of the 31.9 GiB on 1 RTX PRO 4500 Blackwell card. Measured on the deployed server, the remaining KV pool holds **675,376 tokens** at `block_size=16` across 42,211 GPU blocks, which is **82 concurrent sequences** at the recipe's 8,192 token context. Those figures come from the `KV capacity from` and `KV full-ctx seqs` lines of the provenance block, and they are authoritative over any arithmetic.

The estimate that sized this recipe predicted 54 sequences, from a 7.8 GiB pool assuming a 6 GiB runtime reserve. The server allocates more than that, so the reserve is nearer 2 GiB than 6 on a single-GPU TP1 deployment with no NCCL buffers. Treat the per-token cost below as sound and the reserve term as the loose one.

| Property | Value | Source |
|---|---|---|
| **Parameters** | 4B active | Model card |
| **Layers** | 42, of which 7 full attention and 35 sliding at window 512 | `config.json`, `text_config.layer_types` |
| **KV-owning layers** | 24; the last 18 share KV with earlier layers | `config.json`, `text_config.num_kv_shared_layers` |
| **KV heads, head dimension** | 2; 256 sliding, 512 full attention | `config.json`, `head_dim` and `global_head_dim` |
| **Checkpoint size, BF16** | 14.89 GiB, one safetensors file | `model.safetensors` blob size |
| **Instance** | g7.2xlarge, 1x RTX PRO 4500 Blackwell at 32 GB | 32 GB nominal, 31.9 GiB |
| **Tensor parallel size** | 1 | unset, single GPU |
| **Weight precision** | BF16 | `DTYPE`, pinned `--dtype bfloat16` |
| **KV cache precision** | BF16, 16-bit | `KV_CACHE_DTYPE=auto`, follows `DTYPE` |
| **Context length** | 8,192 | `MAX_MODEL_LEN`, model supports 131,072 |
| **Memory fraction** | 0.90 | `GPU_MEM_UTIL` |
| **Max sequences** | 512 | `MAX_NUM_SEQS` |

KV cache per layer per token is `2 x kv_heads x head_dim x bytes_per_element`, which is 2 KiB on a sliding layer and 4 KiB on a full attention layer, since the two use different head dimensions. Two properties of E4B make its cache far cheaper than the layer count suggests: the last 18 of 42 layers share KV with earlier layers, so only 24 layers own a cache, and the 20 sliding layers among those hold at most 512 tokens whatever the context length. Only the 4 full attention layers that own a cache grow with context, so one 8,192-token sequence costs 0.145 GiB, against 0.520 GiB at 32,768 and 2.020 GiB at the full 131,072.

## Before you begin

Create the following in the namespace you deploy into. Secrets and ConfigMaps are namespaced.

- Create a `g7.2xlarge` node group in a subnet with free IPs; the AZ this instance's capacity lands in may have none by default, so check first. Use a launch template so the instance store is mounted, see below
- [Apply the `nvidia-open-driver-healer` DaemonSet](../../../k8s/examples/daemonset-nvidia-open-driver.yaml). The AL2023 NVIDIA AMI ships the closed kernel module, which Blackwell does not support, so without this the node advertises no GPU indefinitely rather than failing loudly
- [Create the `vllm-sitecustomize` ConfigMap](../../../k8s/examples/configmap-vllm-sitecustomize.yaml)

No FSx PVC in this runbook. The recipe downloads its own weights into an `emptyDir` on the instance store, the same pattern `gemma4-31b/bf16-g7e.2xlarge.yaml` uses, because no FSx for Lustre filesystem exists in every AZ this instance type's capacity might land in.

## Quickstart

1. Set environment variables.

   ```bash
   export AWS_REGION=<your-cluster-region>
   export EKS_CLUSTER_NAME=<your-cluster-name>
   export HUGGING_FACE_HUB_TOKEN=<your-hf-token>
   export NAMESPACE=vb-gemma4-e4b-bf16-g7-2xlarge
   export INSTANCE_TYPE=g7.2xlarge
   ```

2. Configure the EKS context and namespace, install the NVIDIA Kubernetes device plugin, and create the `hf-token` secret.

   ```bash
   ./scripts/install-prerequisites.sh
   ```

3. Confirm the sitecustomize ConfigMap exists in the namespace.

   ```bash
   kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" get configmap vllm-sitecustomize
   ```

4. Deploy and validate the model server. Its init container downloads the weights into pod-local (`emptyDir`) storage before vLLM starts, so the first rollout takes as long as the download and pod replacement downloads them again.

   ```bash
   ./vllm-recipes/gemma4-e4b/bf16-g7.2xlarge-deploy.sh
   ```

5. Generate the accuracy gate (.JSON) required for the next step.

   ```bash
   eks-bench capture-reference \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" --service gemma4-e4b-vllm-g7-2xl-bf16 \
       --mode fingerprint \
       --model-tag gemma4-e4b --config bf16 \
       --model-id /models/gemma-4-E4B-it \
       --out-dir docs/results
   ```

6. Dry-run the in-cluster benchmark. This validates and renders the Job without creating cluster resources.

   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" --service gemma4-e4b-vllm-g7-2xl-bf16 \
       --protocol corpus --profile legacy_corpus \
       --instance g7.2xlarge --model-tag gemma4-e4b \
       --config bf16 --quant bf16 \
       --model-id /models/gemma-4-E4B-it \
       --tokenizer google/gemma-4-E4B-it \
       --reps 3 --out-dir docs/results \
       --dry-run
   ```

7. Run the benchmark in-cluster. If needed, repeat per protocol, changing `--protocol` and `--profile`.

   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" --service gemma4-e4b-vllm-g7-2xl-bf16 \
       --protocol corpus --profile legacy_corpus \
       --instance g7.2xlarge --model-tag gemma4-e4b \
       --config bf16 --quant bf16 \
       --model-id /models/gemma-4-E4B-it \
       --tokenizer google/gemma-4-E4B-it \
       --reps 3 --out-dir docs/results
   ```

## Tear down

```bash
kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" delete -f vllm-recipes/gemma4-e4b/bf16-g7.2xlarge.yaml
```

## Settings

- **`image: public.ecr.aws/deep-learning-containers/vllm:0.21.0-gpu-py312`** Same image as the Gemma 4 31B deployments, which serve the same architecture family. Verify this DLC ships the Gemma 4 model module before relying on it; bump the tag if not.
- **`- --dtype bfloat16`** Pinned rather than inferred from the checkpoint, so the manifest states the precision outright. `bfloat16` is not an arbitrary choice of 16-bit format: Gemma's activations exceed float16's 65,504 ceiling, and vLLM has an open defect where [Gemma 4's vision tower overflows under fp16](https://github.com/vllm-project/vllm/issues/40290). Follows the `qwen2.5-7b/bf16-*.yaml` recipes, which pin the same way.
- **`- --kv-cache-dtype auto`** Pinned to `auto`, which resolves to the weights dtype above and so yields a BF16 cache. The literal value `bfloat16` is [documented as valid only for models that default to FP8](https://docs.vllm.ai/en/v0.21.0/api/vllm/config/cache/), which E4B does not, so pinning `--dtype` is what actually fixes the cache precision. FP8 KV would roughly halve the per-sequence cost but changes accuracy, so it belongs in its own recipe with its own reference fingerprint rather than as a flag flip here.
- **`- --gpu-memory-utilization=0.90`** Lower than the 0.95 the 31B recipes use, because a 32 GiB card leaves less absolute headroom for activations and CUDA graphs once weights are resident. No `--quantization`: this serves the unquantized checkpoint.

- **`nvidia.com/gpu: 1`** g7.2xlarge = 1x Blackwell RTX PRO 4500, 32GB (sm_120). This is a third the memory of the RTX PRO 6000 in the g7e family, which is why the memory fraction and batched-token budget differ from the 31B recipes.
- **`- --max-num-seqs=512`** Matched to the other Gemma configs so the swept concurrency, not this ceiling, is what binds.
- **`VLLM_ATTENTION_BACKEND=FLASHINFER`** Required for Blackwell sm_120.
- **Multimodal towers** E4B ships vision (16 layers) and audio (12 layers) encoders alongside the 42 text layers. The benchmark protocols send text only, so those towers are resident but idle; their weights are already counted in the 14.89 GiB checkpoint.
