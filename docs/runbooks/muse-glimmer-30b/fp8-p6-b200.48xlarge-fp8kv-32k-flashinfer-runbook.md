# Muse-Glimmer-30B FP8 with an FP8 KV cache on one B200 GPU, FlashInfer attention

Serves a locally quantized ModelOpt FP8 build of [`meta-models/Muse-Glimmer-30B`](https://huggingface.co/meta-models/Muse-Glimmer-30B) on one GPU of a p6-b200.48xlarge, using [`fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer.yaml`](../../../vllm-recipes/muse-glimmer-30b/fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer.yaml).

## Capacity sizing

Muse-Glimmer-30B is dense and its KV cache is light. 2 KV heads at head size 128 across 52 layers cost 26 KiB per token at FP8, so a full 32,768-token sequence holds 0.81 GiB. At a 0.90 memory fraction, one 180 GB B200 leaves roughly 118 GiB after the 32 GiB checkpoint, before activations and CUDA graphs. That is room for about 140 full-length sequences, so the 64-sequence cap, not memory, bounds the batch. Read `KV capacity from` and `KV full-ctx seqs` in the result file's provenance block for the allocation in force.

`coding_repo_context` sends about 14.5k wire input tokens and asks for up to 1,024 output tokens. Prompt processing, not KV memory, is the limit for this workload.

| Property | Value | Source |
|---|---|---|
| **Parameters** | ~29.6B dense, including a 1.8B image encoder | `config.json`; no expert or router settings |
| **Layers** | 52 | `config.json` |
| **KV heads, head dimension** | 2, 128 | `config.json` |
| **KV cache per token, FP8** | 26 KiB | `2 x 2 x 128 x 1 byte x 52 layers` |
| **Checkpoint size, FP8** | ~32 GiB, 4 safetensors shards | `fetch-weights` init container checks |
| **Instance** | p6-b200.48xlarge, 1 of 8 B200 GPUs at 180 GB, sm_100 | `nvidia.com/gpu: "1"` |
| **Weight precision** | FP8 E4M3, ModelOpt export | `QUANTIZATION` |
| **KV cache precision** | FP8 E4M3, uncalibrated scales | `KV_CACHE_DTYPE`; see Settings |
| **Attention backend** | `FLASHINFER` | `ATTENTION_BACKEND` |
| **Context length** | 32,768 | `MAX_MODEL_LEN` |
| **Max sequences** | 64 | `MAX_NUM_SEQS` |
| **Memory fraction** | 0.90 | `GPU_MEM_UTIL` |
| **Stream interval** | 10 tokens | `STREAM_INTERVAL` |

## Before you begin

Create the following in the namespace you deploy into. Secrets and ConfigMaps are namespaced.

- [Create a `p6-b200.48xlarge` node group](../../../k8s/examples/eksctl-nodegroup-gpu-spot.yaml) (set the instance type)
- [Mount its instance store as RAID0 for kubelet storage](../../../k8s/examples/nodeconfig-local-nvme-raid0.yaml)
- [Create a benchmark-client node group](../../../k8s/examples/eksctl-nodegroup-bench-client.yaml) (the client Job does not tolerate the GPU taint)
- [Install the EKS Pod Identity Agent add-on](https://docs.aws.amazon.com/eks/latest/userguide/pod-id-agent-setup.html)
- [Associate an S3 read role with the `muse-glimmer-30b-bench` ServiceAccount in your namespace through Pod Identity](https://docs.aws.amazon.com/eks/latest/userguide/pod-id-association.html)
- [Create a `g7e.2xlarge` node group for quantization](../../../k8s/examples/eksctl-nodegroup-g7e-2xl-spot.yaml) (only if the checkpoint is not in S3 yet)
- [Install the FSx CSI driver and create the `fsx-pvc` claim](../../../k8s/examples/README.md#creating-the-weights-filesystem) (only if the checkpoint is not in S3 yet)
- [Grant S3 write access to the staging Job](https://docs.aws.amazon.com/eks/latest/userguide/pod-id-association.html) (only if the checkpoint is not in S3 yet)

## Quickstart

1. Set environment variables.
   ```bash
   export AWS_REGION=<your-cluster-region>
   export EKS_CLUSTER_NAME=<your-cluster-name>
   export HUGGING_FACE_HUB_TOKEN=<your-hf-token>
   export NAMESPACE=vb-muse-glimmer-30b-fp8kv-32k-flashinfer-p6-b200-48xlarge
   export INSTANCE_TYPE=p6-b200.48xlarge
   export WEIGHTS_BUCKET=<your-weights-bucket>
   export WEIGHTS_REGION=<your-weights-bucket-region>
   ```

2. Install the `eks-bench` CLI into a Python virtual environment.
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -e '.[tokenizer]'
   ```

3. Configure the EKS context and namespace, install the NVIDIA device plugin, and create the `hf-token` secret.
   ```bash
   ./scripts/install-prerequisites.sh
   ```

4. Quantize the model to ModelOpt FP8 and save the checkpoint to the `fsx-pvc` claim.
   ```bash
   ./model-jobs/muse-glimmer-30b/fp8-model-quantize.sh
   ```

5. Copy the quantized checkpoint from the claim to your S3 bucket.
   ```bash
   ./model-jobs/muse-glimmer-30b/fp8-model-fsx-to-s3.sh
   ```

## Throughput test

1. Deploy the vLLM inference server and confirm it serves the model.
   ```bash
   ./vllm-recipes/muse-glimmer-30b/fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer-deploy.sh
   ```

2. Generate the accuracy gate (.JSON) that the benchmark checks against.
   ```bash
   eks-bench capture-reference \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service muse-glimmer-30b-vllm-b200-fp8kv-32k-flashinfer \
       --mode fingerprint \
       --model-tag muse-glimmer-30b --config fp8kv-32k-flashinfer \
       --model-id muse-glimmer-30b \
       --out-dir docs/results
   ```

3. Dry-run the exact in-cluster benchmark.
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service muse-glimmer-30b-vllm-b200-fp8kv-32k-flashinfer \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag muse-glimmer-30b \
       --config fp8kv-32k-flashinfer --quant fp8 \
       --model-id muse-glimmer-30b \
       --tokenizer meta-models/Muse-Glimmer-30B \
       --out-dir docs/results \
       --reps 3 \
       --dry-run
   ```

4. Run the benchmark in-cluster. If needed, repeat per protocol, changing `--protocol` and `--profile`.
   ```bash
   eks-bench measure \
       --context "$EKS_CLUSTER_NAME" --namespace "$NAMESPACE" \
       --service muse-glimmer-30b-vllm-b200-fp8kv-32k-flashinfer \
       --protocol corpus --profile coding_repo_context \
       --instance p6-b200.48xlarge --model-tag muse-glimmer-30b \
       --config fp8kv-32k-flashinfer --quant fp8 \
       --model-id muse-glimmer-30b \
       --tokenizer meta-models/Muse-Glimmer-30B \
       --out-dir docs/results \
       --reps 3
   ```

## Tear down

```bash
kubectl --context "$EKS_CLUSTER_NAME" -n "$NAMESPACE" delete \
    -f vllm-recipes/muse-glimmer-30b/fp8-p6-b200.48xlarge-fp8kv-32k-flashinfer.yaml --ignore-not-found
aws eks update-nodegroup-config --cluster-name "$EKS_CLUSTER_NAME" --nodegroup-name gpu-spot-1node \
    --region "$AWS_REGION" --scaling-config minSize=0,maxSize=1,desiredSize=0
```

Scale the quantization and benchmark-client node groups to zero too if you created them for this run. The checkpoint in S3 survives, so a later run skips Quickstart steps 4 and 5.

## Settings

- **`source .venv/bin/activate`** Puts `eks-bench` on your PATH in the current terminal only. If you open a new terminal, run it again from the repository root before continuing.
- **One GPU of eight.** The other seven B200 GPUs stay idle unless something else schedules onto them, so this is a per-GPU figure, not a per-node one.
- **The backend is pinned with `--attention-backend`, not `VLLM_ATTENTION_BACKEND`.** vLLM 0.29.0 does not read that environment variable and falls back to its auto-selected backend. The deploy script fails unless the server logs `Using AttentionBackendEnum.FLASHINFER backend`.
- **`--stream-interval 10`** The server streams in 10-token chunks, where the g7e recipes stream token by token. That changes inter-token latency only, so never compare ITL between this recipe and the g7e ones.
- **`GPU_MEM_UTIL=0.90`, against 0.95 on g7e.** The B200 pool is large enough that the 64-sequence cap binds first, so the difference does not change the batch.
- **KV scales are uncalibrated.** vLLM 0.29.0 rejects `--calculate-kv-scales`, so the server logs `Using KV cache scaling factor 1.0 for fp8_e4m3`. This bounds any quality comparison.
- **`--no-enable-prefix-caching`** Held off for an uncached measurement. Confirm `Prefix cache hit` reads 0.0% in the provenance block before publishing any figure.
- **`MAX_NUM_SEQS=64`, `MAX_CUDAGRAPH=64` and `MAX_NUM_BATCHED_TOKENS=32768`.** Held at the g7e values so the batch ceiling and prefill chunk are not variables between the two GPUs.
- **`--served-model-name muse-glimmer-30b`** The server answers to that name rather than its path, so `--model-id` is `muse-glimmer-30b` here and a path on the g7e recipes.
- **Weights come from S3 into an `emptyDir`, not from the claim.** A pod restart re-downloads 32 GiB. The `fetch-weights` init container fails unless it finds 4 shards and at least 28 GiB.
- **`serviceAccountName: muse-glimmer-30b-bench`** Supplies the pod-scoped S3 read identity through EKS Pod Identity. Node roles on clusters with an IMDS hop limit of 1 are unreachable from pods.
- **`WEIGHTS_BUCKET` and `AWS_REGION` are placeholders in git.** The staging and deploy scripts fill them in from `WEIGHTS_BUCKET` and `WEIGHTS_REGION` as they apply each manifest, so the files in git stay untouched.
- **The S3 staging Job sets no ServiceAccount.** It runs as the namespace's `default` ServiceAccount, so that is the identity the write role must be associated with.
- **The quantize Job runs in the serving image.** The quantizer image's transformers predates `model_type: muse_glimmer`, so the Job installs ModelOpt and a newer transformers into `vllm/vllm-openai:v0.29.0` at start. It keeps the image encoder, projector, embeddings and head in 16-bit.
